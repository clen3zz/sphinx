# 第 3 周规格：最小可观测性与可复现基准

- 状态：Completed（2026-08-24）
- 依赖：第 2 周规格全部验收通过
- 目标：让当前服务能够回答“处理了什么请求”和“在明确负载下表现如何”，但不建设工业级监控系统

## 1. 范围

本周只交付三项内容：

1. 一个最小 `stats` 命令；
2. 一个调用成熟 Memcached 压测客户端的本地基准脚本；
3. 一份记录环境、负载和结果的基准文档。

本周不以达到某个 QPS 或延迟数字为完成条件，也不要求为了数字主动重构服务端。

## 2. 模块 A：服务级统计

### 2.1 协议

新增命令：

```text
stats\r\n
```

响应必须使用固定顺序：

```text
STAT version <version>\r\n
STAT threads <worker_count>\r\n
STAT limit_maxbytes <configured_bytes>\r\n
STAT cmd_get <count>\r\n
STAT get_hits <count>\r\n
STAT get_misses <count>\r\n
STAT cmd_set <count>\r\n
STAT cmd_add <count>\r\n
STAT cmd_replace <count>\r\n
STAT cmd_delete <count>\r\n
STAT cmd_incr <count>\r\n
STAT cmd_decr <count>\r\n
END\r\n
```

### 2.2 计数语义

- **W3-STATS-01**：统计对象必须由所有工作线程共享，响应表示整个进程的汇总值，而不是当前连接线程的局部值。
- **W3-STATS-02**：`cmd_get` 按客户端 `get` 命令计数；一个多键 `get` 只增加 1。
- **W3-STATS-03**：`get_hits`、`get_misses` 按键计数；重复键的每次出现分别计数。
- **W3-STATS-04**：`cmd_set`、`cmd_add`、`cmd_replace`、`cmd_delete`、`cmd_incr`、`cmd_decr` 均按收到并开始执行的客户端命令计数，不因成功或失败而改变计数规则。
- **W3-STATS-05**：非法语法、尚未收完整的请求和 `stats` 自身不增加上述计数。
- **W3-STATS-06**：所有计数从 0 开始，使用无符号 64 位原子计数；并发增加不得丢失。
- **W3-STATS-07**：统计响应是逐项读取的弱一致快照，不要求所有字段来自同一瞬间，但每个字段自身不得产生数据竞争或撕裂读取。
- **W3-STATS-08**：`threads` 和 `limit_maxbytes` 必须等于启动参数最终生效的值。

### 2.3 最小设计约束

- 可以增加一个只保存配置和原子计数器的 `ServerStats` 对象，由所有 `Server` 实例引用。
- 计数器使用 `memory_order_relaxed` 即可；统计不参与业务同步。
- 不统计当前对象数、实时内存占用和淘汰数，因为现有整段回收与惰性过期会使这些指标需要额外维护逻辑。
- 不引入 Prometheus、HTTP 管理端口、日志框架、指标标签或后台采样线程。

### 2.4 直接测试

- 单元测试：所有字段初始为 0；多线程并发增加后的总数精确；响应顺序固定。
- `protocol_test.cpp`：完整、分片和流水线中的 `stats`。
- `network_test.py`：在新进程中执行一组确定的命令，断言配置字段和全部计数；4/8 线程并发后断言汇总值无丢失。

## 3. 模块 B：本地端到端基准脚本

### 3.1 工具选择

新增 `scripts/run_local_benchmark.py`，负责启动本地 `sphinxd` 并调用
[memtier_benchmark](https://github.com/RedisLabs/memtier_benchmark)。脚本只负责编排、参数检查和保存结果，不自行实现高性能压测客户端。

现有 `scripts/mutilate.py`、`scripts/memaslap.py` 保留作为历史工具，但不作为本周验收入口，也不扩展其远程 SSH 功能。

### 3.2 功能需求

- **W3-BENCH-01**：脚本必须接收服务端可执行文件、工作线程数、内存、段大小、测试时长、客户端线程数、连接数、键空间和值大小。
- **W3-BENCH-02**：脚本必须使用空闲的本地 TCP 端口启动服务，确认服务可连接后再开始预填充和测量。
- **W3-BENCH-03**：调用 memtier 时必须显式选择 `memcache_text` 协议，不能依赖工具默认协议。
- **W3-BENCH-04**：脚本只提供三种固定工作负载：
  - `read`：预填充后只读；
  - `mixed`：预填充后 90% `get`、10% `set`；
  - `write`：只执行 `set`。
- **W3-BENCH-05**：每次运行必须保存 memtier 的原始 JSON 结果，并另存运行元数据：Git 提交、服务端参数、客户端参数、工作负载和开始时间。
- **W3-BENCH-06**：memtier 非零退出、服务提前退出、结果文件缺失或协议错误数非零时，脚本必须以非零状态结束，不得输出“成功”结果。
- **W3-BENCH-07**：无论成功还是失败，脚本必须停止自己启动的服务进程；不得用模糊进程名杀死其他实例。
- **W3-BENCH-08**：脚本必须提供 `--dry-run`，打印将执行的命令但不启动服务或客户端。
- **W3-BENCH-09**：性能结果不与固定阈值比较；不同机器的数字不得直接判定为功能回归。

### 3.3 固定基线配置

用于项目文档的默认基线为：

| 参数 | 值 |
| --- | --- |
| 服务线程 | 4 |
| 缓存内存 | 64 MiB |
| Segment | 2 MiB |
| Key space | 100,000 |
| Value size | 256 B |
| Client threads | 4 |
| Connections per client thread | 8 |
| 测量时间 | 20 s |
| 重复次数 | 3 |

三次结果使用中位数展示，同时保留三份原始结果。该配置用于可复现对比，不代表生产负载或容量上限。

### 3.4 直接测试

新增 Python `unittest` 并接入 CTest，至少覆盖：

1. 参数合法性与非法值拒绝；
2. 三种工作负载生成的 memtier 参数；
3. `--dry-run` 不创建进程和结果文件；
4. 使用伪造 memtier 可执行文件验证 JSON 保存、非零退出和协议错误处理；
5. 3 秒、小键空间的本地冒烟运行，确认服务可启动、结果可生成且协议错误为 0。

默认 `ctest` 中的冒烟测试只有检测到 `memtier_benchmark` 时才运行；参数、进程清理和结果校验测试不得依赖外部工具，必须始终运行。

## 4. 交付物 C：基准结果文档

新增 `BENCHMARK.md`，每次正式基线至少记录：

- CPU 型号、逻辑核数、内存、操作系统和编译器；
- 构建类型、Git 提交和完整启动参数；
- 工作负载、键空间、值大小、客户端并发和测试时长；
- 三次运行的 QPS、P50、P95、P99 和协议错误数；
- 中位数结果；
- 已知限制，例如客户端与服务端运行在同一台机器。

### 4.1 文档约束

- **W3-DOC-01**：不得只保留最好的一次结果。
- **W3-DOC-02**：不得把微基准耗时写成端到端 QPS。
- **W3-DOC-03**：不同负载必须分别命名，不能把读、混合和写三组数字并列为同一个“峰值”。
- **W3-DOC-04**：没有同配置对照数据时，不使用“提升百分之多少”的表述。
- **W3-DOC-05**：若根据分析进行优化，必须用同一提交之外的前后两个版本、相同配置重新测量，并且完整功能测试仍通过。

文档模块的验收证据是三种工作负载各三份原始 JSON、对应元数据文件以及由这些文件抄录的表格；不得手工编造数字。

## 7. 完成定义

- `stats` 在并发下计数准确，并由自动化测试证明；
- 基准脚本失败时不会留下服务进程；
- 三种负载均能生成可解析且协议错误为 0 的结果；
- `BENCHMARK.md` 中每个数字都能追溯到保存的原始结果；
- 不以性能阈值掩盖功能错误；
- README 同步标记 `stats` 和基准工具状态。
