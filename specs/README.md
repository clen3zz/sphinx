# Sphinx 四周规格驱动开发索引

## 1. 项目目标

本项目计划在四周内完成一个便于学习、演示和面试讲解的 C++ 内存缓存：

1. 单机多线程缓存的核心读写语义正确；
2. 具备可复现的功能测试和性能基线；
3. 通过静态客户端路由演示跨节点分片；
4. 所有结论都能由代码和测试证明。

项目不以替代 Memcached、Redis 或构建工业级缓存平台为目标。这里的“正确”是指：在规格明确支持的输入、资源范围和静态配置内，程序行为与规格一致；不包括极端资源耗尽、高可用和在线运维能力。

## 2. 当前基线

第 1 周已经完成，基线提交为 `11a75a5`：

- `set`、`add`、`replace`、单键 `get`、`version`；
- `flags`、相对 TTL、绝对过期时间；
- 1/4/8 工作线程下的键分片和跨线程消息传递；
- TCP 分包、粘包、流水线、部分写、连接提前关闭；
- 请求背压、连接内响应排序、日志内存回收和索引覆盖修复；
- 单元测试、真实 TCP 集成测试以及 ASan/UBSan/TSan 验证。

后续规格只在此基线上增量开发，不重写已有 Reactor、日志结构化内存分配器或协议框架。

## 4. 规格驱动流程

每个模块必须按以下顺序开发：

1. **冻结行为**：先确认需求编号、输入、输出、状态变化、错误语义和非目标。
2. **先写测试**：为该模块增加规格中列出的测试，并确认测试在功能实现前能够失败。
3. **最小实现**：只编写让这些测试通过所需的代码，不预留尚未进入规格的抽象层。
4. **完整回归**：模块测试、当周集成测试和原有全部测试必须完整运行到结束。
5. **更新事实文档**：功能通过验收后，才把 README 中对应项目从“待实现”改为“已支持”。

需求发生变化时，先修改规格和测试矩阵，再修改实现。禁止先写额外功能、事后补规格。

## 5. 规格用词

- **必须**：验收所需行为，缺失即模块未完成。
- **不得**：明确禁止的行为或范围。
- **可以**：不影响验收的实现选择，但不得扩大公开接口或引入新的运行依赖。
- **非目标**：本周期不会实现，也不应以空接口、占位类或 TODO 代码提前搭建。

## 6. 测试分层

每个模块至少有一种直接测试，并按需要增加跨模块测试：

| 测试层级 | 负责证明的内容 | 执行方式 |
| --- | --- | --- |
| 单元测试 | 解析、数据结构、状态变化和边界条件 | GoogleTest 或 Python `unittest` |
| 网络集成测试 | 命令经过真实 TCP、Reactor、跨线程路由和存储后的完整行为 | Python 启动真实 `sphinxd` |
| 多节点集成测试 | 静态路由、节点隔离和失败返回 | Python 启动多个 `sphinxd` 进程 |
| 基准冒烟测试 | 基准命令、结果文件和错误检测可正常工作 | 短时本地运行，不设置性能门槛 |

不允许用手工演示代替自动化正确性测试。性能数字也不能替代功能断言。

## 7. 通用验收门槛

每周完成时必须满足：

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j"$(nproc)"
ctest --test-dir build --output-on-failure

cmake -S . -B build-asan -DCMAKE_BUILD_TYPE=Debug
cmake --build build-asan -j"$(nproc)"
ctest --test-dir build-asan --output-on-failure
```

同时必须确认：

- 新增模块在对应规格的测试矩阵中都有直接测试；
- 原有命令和 1/4/8 线程网络测试无回归；
- 测试进程退出码为 0，且无 ASan 报告；
- `git diff --check` 通过；
- README 的“已支持”和“待实现”与代码一致。

性能提升不是通用验收门槛。第 3 周只要求基准可复现、无协议错误并完整记录环境，不要求达到预设 QPS。

## 8. 本周期统一非目标

以下能力不属于剩余三周，不得为了“以后可能需要”提前设计：

- 完整 Memcached ASCII、Binary 或 Meta 协议；
- UDP、TLS、鉴权和公网部署；
- 持久化、WAL、快照和缓存预热；
- 服务端代理、服务发现、动态成员变更和在线配置中心；
- 副本、一致性协议、自动故障转移、请求重试和数据迁移；
- 跨机房、高可用、无损升级和生产级监控告警；
- CUDA、Tensor 存储、Prefix Cache 等 LLM KV Cache 能力；
- 对 `std::bad_alloc`、文件描述符耗尽等极端资源故障作工业级恢复保证。

如果后续确实需要其中某项，应建立新的独立规格，不得直接扩充当前模块。
