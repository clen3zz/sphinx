# Redis 与 Sphinx：商品 HTTP 和直接缓存路径性能实验

## 结论

在本次 **单核缓存预算、Release、本机回环网络、并发 16** 的测试中：

- 直接缓存 GET 和 SET 的吞吐处于同一数量级，Redis 中位数分别高 7.6% 和 3.9%。
  三次采样范围存在重叠，不能据此断言单项操作有普遍或统计显著的优势。
- 32 项直接读取中 Redis 吞吐高 44.2%；32 项批量写入中 Redis 是 Sphinx 的 8.23 倍。
  后者包含 Redis pipeline 与 Sphinx 逐条等待 set 确认的差别，不是存储引擎速度比。
- 完整 HTTP 单项命中中 Redis 吞吐低 5.0%，32 项批量命中中 Redis 高 10.7%。
  后端直接访问的差距没有按同样比例传递到 HTTP 链路。
- 并发从 16 提高到 64 后，多数场景吞吐不再提升，P99 明显增大。不能把最高并发当成最佳配置。

本次回答的是当前项目路径在明确条件下的性能。它不证明某个缓存引擎全面更快，也不代表
多节点、多 Worker、持久化或远程网络部署下的性能。

## 实验设计与环境

| 条件 | 设置 |
| --- | --- |
| 时间 | 2026-10-01；原始 JSON 保存 UTC 开始时间 |
| 环境 | WSL2，Linux 6.18.33.2，Intel Core Ultra 5 245K，14 个可用逻辑 CPU |
| 构建 | Sphinx、商品服务和 C++ 负载程序为 Release，项目配置使用 `-O3 -g -DNDEBUG` |
| 软件 | GCC 15.2.0；Redis 8.0.5 / jemalloc 5.3.0；MySQL 8.4.11 |
| 被测代码 | `9aeaa56861b04f813bc0ab140e26f49092e822df` 上的商品服务与节点实现；新增负载程序的 SHA-256 见原始 JSON |
| 缓存预算 | 每个后端使用同一个客体逻辑 CPU 0；Sphinx 一个 Worker，Redis `io-threads=1` |
| 其他 CPU | HTTP 使用 1、2；MySQL 使用 3、4；负载程序使用 5～12；观察进程使用 13 |
| 商品服务 | 固定 4 个 HTTP Worker，basic 策略 |
| 数据 | 4096 个商品或 key；直接组 value 为 256 字节；HTTP 组读取同一份商品数据 |
| 缓存配置 | 64 MiB 预算；TTL 300 秒；Redis noeviction、关闭 RDB 与 AOF；数据集完整预热 |
| 并发 | 1、4、16、64 个客户端线程，每线程最多一个在途操作，闭环负载 |
| 时间与重复 | 每次预热 1 秒，测量 5 秒，同条件重复 3 次；每次重新启动缓存和 HTTP 服务 |
| 顺序 | 条件顺序及成对后端顺序按固定随机种子打乱 |
| 汇总 | 吞吐、P50/P95/P99 分别取三次采样中位数；同时保留吞吐最小～最大范围 |

Redis 使用现成发行版二进制，没有声称其编译参数与 Sphinx 完全相同。CPU 亲和性限制的是
WSL 客体逻辑 CPU，不是宿主物理核；不能完全排除宿主机调度、功耗与其他应用影响。

正式数据共 168 次采样，累计 **53,808,807 次成功 API/HTTP 操作**，测量窗口合计
840.126 秒。测量与预热错误数均为零。批量操作按一次 API 调用计数，一次包含 32 项，
不是把每项都计成一个批量请求。

## 第一组：完整商品 HTTP 读链路

```text
C++ HTTP 客户端
  → TCP 建连、HTTP 解析和线程调度
  → ProductService
  → Sphinx 或 Redis 缓存适配器
  → 缓存节点
  → HTTP JSON 响应与连接关闭

fresh=1：跳过缓存读取 → 查询 MySQL → 尽力回填缓存 → HTTP 响应
```

HTTP 客户端每请求建立连接，包含建连和关闭成本；商品服务到 MySQL、缓存的连接仍复用。
最初试用长连接时发现：当前固定线程池在等待下一条请求时仍占用 Worker，所有 Worker
被预热后的空闲长连接占住后，指标请求无法处理。正式实验因此统一使用短连接，并重新运行
全部采样；中止试跑的两个直接缓存样本没有混入正式数据。

以下统一比较并发 16。吞吐单位为 **HTTP 请求/秒**，延迟为整个 HTTP 请求的 P99。
Redis 相对变化统一以 Sphinx 为分母。

| 场景 | Sphinx 请求/s | Redis 请求/s | Redis 吞吐变化 | Sphinx P99 | Redis P99 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 单项缓存命中 | 37,652 | 35,781 | −5.0% | 0.917 ms | 0.935 ms |
| 32 项批量命中 | 15,503 | 17,167 | +10.7% | 1.927 ms | 1.723 ms |
| fresh 查询并回填 | 14,366 | 13,907 | −3.2% | 1.983 ms | 2.006 ms |

单项命中三次吞吐范围分别为 Sphinx 37,484～37,751、Redis 35,593～36,223 请求/s；
批量命中分别为 14,409～16,070、15,265～17,211 请求/s。批量存在波动，10.7% 是这次
实验的中位数差距，不是对所有环境的固定增益。

所有命中样本都核对实际 MySQL SELECT 为零；所有 fresh 样本都核对 SELECT 次数等于
成功请求数。fresh 仍写缓存，因此是共同数据库读路径的控制场景，不是纯 MySQL 实验。
本组覆盖单项、批量和主动核实的 HTTP 读流程，没有测 PUT 事务吞吐。

## 第二组：直接缓存读写路径

```text
C++ 负载线程
  → 当前项目的 SphinxProductCache / RedisProductCache
  → ClusterClient / hiredis
  → TCP、协议解析与缓存处理
  → 返回值校验
```

这一组绕过 HTTP、JSON 商品处理和 MySQL，使用每线程独占的长连接。仍包含适配器、
客户端、协议、网络与回复校验，不是引擎内部微基准。每次 GET 校验 256 字节 value，
批量读校验返回长度和全部 value；写操作要求客户端确认成功。

以下同样统一并发 16。单项单位为操作/s，批量单位为 **32 项 API 调用/s**；P99 对应
一次调用完成的时间。

| 场景 | Sphinx 调用/s | Redis 调用/s | Redis 吞吐变化 | Sphinx P99 | Redis P99 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 单项 GET | 223,890 | 240,928 | +7.6% | 222.4 μs | 178.2 μs |
| 单项 SET | 230,540 | 239,536 | +3.9% | 218.9 μs | 181.8 μs |
| 32 项读取 | 98,262 | 141,678 | +44.2% | 419.0 μs | 293.8 μs |
| 32 项回填 | 7,290 | 59,967 | +722.6%，即 8.23 倍 | 4,332.4 μs | 574.9 μs |

32 项读取换算为约 314 万项/s 与 453 万项/s；32 项写入换算为约 23.3 万项/s 与
191.9 万项/s。这些是同一批量实验的换算，不是另一次单项操作实验。

单项 GET 三次范围为 Sphinx 221,047～239,199、Redis 237,417～251,446 调用/s；单项
SET 为 216,644～235,221、226,773～241,920 调用/s，存在重叠。多键读取范围为
97,739～98,444、140,635～141,761 调用/s，这次差距比单项更稳定。

批量回填中，Redis 先发送 pipeline，再顺序读完回复；Sphinx 当前对每条 set 等待确认。
差距包含往返次数、客户端实现、协议处理和节点存储成本。不能写成“Redis 的 SET 引擎
比 Sphinx 快 8.23 倍”；相同并发的单项 SET 只观察到 3.9% 中位数差距。

## 并发增加后的表现

下表展示两个代表场景；所有场景与并发档位见 [完整汇总](SUMMARY.md)。

| 场景与后端 | 并发 16 调用/s | 并发 64 调用/s | 并发 16 P99 | 并发 64 P99 |
| --- | ---: | ---: | ---: | ---: |
| HTTP 单项命中，Sphinx | 37,652 | 37,458 | 0.917 ms | 2.762 ms |
| HTTP 单项命中，Redis | 35,781 | 36,144 | 0.935 ms | 2.838 ms |
| 直接 GET，Sphinx | 223,890 | 226,517 | 222.4 μs | 808.8 μs |
| 直接 GET，Redis | 240,928 | 234,100 | 178.2 μs | 706.2 μs |

扫描 1/4/16/64 并发得到的各后端**最高中位吞吐**如下。括号中是产生该数值的并发；
不同后端最高点不一定在同一并发，表中结果也不是已经证明的绝对最大容量。

| 场景 | Sphinx 最高观测调用/s | Redis 最高观测调用/s |
| --- | ---: | ---: |
| HTTP 单项命中 | 37,652（16） | 36,144（64） |
| HTTP 32 项命中 | 15,928（64） | 17,167（16） |
| HTTP fresh | 14,528（64） | 13,907（16） |
| 直接 GET | 226,517（64） | 240,928（16） |
| 直接 SET | 234,248（64） | 239,536（16） |
| 直接 32 项读取 | 98,262（16） | 141,678（16） |
| 直接 32 项回填 | 7,290（16） | 59,967（16） |

这些结果没有指定开放到达率、持续排队上限或 P99 SLA，不能当成 SLA 容量保证。闭环
客户端在响应变慢时会自动降低发送速率，这一点与真实开放流量不同。

## CPU 与内存观察

在并发 16 的四个直接缓存场景中，两个缓存都消耗约 1.00 个 CPU 核，达到设定的单核
预算；负载程序使用约 1.30～3.71 核，低于其 8 个逻辑 CPU 预算。缓存侧饱和与吞吐平台
相互印证，但仍不能完全排除协议和负载程序局部瓶颈。

HTTP 单项和批量命中时，缓存分别只消耗约 0.25～0.32 核；商品 HTTP 进程消耗约
1.31～1.74 核。HTTP 组没有把缓存单核处理能力用满，因此 HTTP 差距不能替代直接缓存
吞吐差距。fresh 场景中 MySQL 消耗约 0.93 核，数据库查询和回填也参与总耗时。

相同 64 MiB 预算不等于相同实际 RSS。并发 16、直接 GET 的采样结束 RSS 中位数约为
Sphinx 68.72 MiB、Redis 15.29 MiB；这是本配置和数据集的进程快照，不是峰值，也不能
单凭它评判内存利用率。Sphinx 的分配方式与 Redis 的动态内存管理不同；写场景中的日志
回收是 Sphinx 实际写路径的一部分。

## 可使用的性能表述与边界

可以表述为：在 WSL2、本机 TCP、单核缓存预算、256 字节 value、并发 16 的 Release
实验中，Sphinx 直接 GET/SET 约为 22.4/23.1 万次每秒，Redis 约为 24.1/24.0 万次每秒；
Redis 多键读取优势更大，批量写入优势包含 pipeline。完整 HTTP 读接口的性能差距更小，
并不总是 Redis 更快。

不能表述为“Sphinx 全面胜过 Redis”“Redis 固定快某个百分比”“商品 HTTP QPS 就是
缓存 QPS”，也不能把单核结果外推到 Sphinx 多 Worker 或多节点部署。

三次采样没有删去异常低值；所有条件中，最大的吞吐最大值/最小值差异约为 40.9%
（直接 GET、并发 4、Redis）。中位数与范围必须一起解读。此次没有做显著性检验、长时间
稳定性测试、PUT 事务负载、淘汰压力或故障场景，不能由本结果推出这些能力的性能。
